# Worked Run

**Recipe:** Reallocation Engine (Job-Search Time Allocator) v0.1.0
**Domain:** Time reallocation for an international job search on OPT, anchored to
Chapter 2 ("The Reallocation Principle") and Chapter 15 ("The Pipeline Tracker
and the Skip Rate") of *The Reallocation Engine*.

## Inputs used

A synthetic population of 240 candidates, generated by `src/generate_candidates.py`
with a fixed seed (7375) for reproducibility. Fields per candidate: network_group
(low/mid/high, based on live_conversations count), live_conversations, weeks_in_search,
hours_available_per_week, visa_constrained, weeks_remaining_on_authorization
(when applicable), portfolio_pieces_deployed_90d, and two book-sourced conversion
constants (base_conversion_cold ≈ 0.2%, base_conversion_referral ≈ 3%, from
Chapter 2). This population is fully synthetic — see "What this data does and
does not capture" below.

## Verified vs. inferred

**Verified (produced directly by code, checkable by re-running):**
- Row counts (240 generated, 213 passed the gate, 27 rejected)
- Every EV, DP_gap, EO_gap, correlation coefficient, and hard-stop fire count
  above — these come directly from arithmetic over the data, not from an LLM's
  judgment
- The GIGO gate's rejection reasons (each tied to a specific, named rule)
- The three hard stops' fire/no-fire status and their conditions

**Inferred / assumed (stated as assumptions, not verified facts):**
- `base_conversion_cold` (0.2%) and `base_conversion_referral` (3%) — sourced
  from Chapter 2's own text, which itself flags these figures with
  `[^verify]` footnotes as needing traceback to a primary source. We did not
  independently verify them; we inherited an unverified number and built on
  top of it. This is named explicitly in `causal_reasoning.py`'s Rung 1/2
  discussion.
- The timing-lag constants used in the explainability critique
  (`COLD_LAG_ZERO_WEEKS` etc.) — explicitly labeled in the code as an
  illustrative modeling assumption, not a measured figure.
- `CALIBRATED_SHIFT_FACTOR` — an empirically-derived number, but derived
  against ONE population sample; component 6 demonstrates this does not
  automatically generalize to a different sample.

## Verification performed

1. **Re-ran the full pipeline from scratch twice** (once during development,
   once independently, per the terminal transcript above) and confirmed
   identical numbers both times — this is what a fixed seed is for, and it
   would have caught any hidden nondeterminism.
2. **Parsed and cross-checked report output against source CSVs** — e.g.
   confirmed the GIGO gate's "213 passed" by counting rows in
   `data/candidates_gated.csv` directly.
3. **Deliberately broke it** (see Attestation below) — edited a value inside
   the already-gated data to simulate a corruption that occurs after the
   quality gate has already run, and observed what happened downstream.

## Attestation

- Recipe: reallocation-engine v0.1.0
- By: Saloni Angre · 2026-07-26

### Tested

| Ran | Saw | Expected |
|---|---|---|
| Full pipeline, `generate_candidates.py` through `delegation_gate.py`, twice independently | Identical numbers both runs (213/213 gated, 93.5% EO_gap reduction, C0032 critique candidate, r=0.1493, Hard Stop 1 on 17/213) | Deterministic, reproducible output |
| GIGO gate against the raw 240-row population | 27 rejected, each with a named reason (bucket mismatch, missing field, out-of-range, duplicate ID, stale conversion constants) | Rejections tied to specific, checkable rules |
| **Deliberate break attempt:** manually edited `data/candidates_gated.csv` — changed candidate C0001's `base_conversion_cold` from 0.002 to 0.9 (a value that has already passed the GIGO gate, simulating post-gate corruption) — then re-ran `allocator.py`, `bias_audit.py`, and `delegation_gate.py` without regenerating or re-gating | The allocator accepted the corrupted value with no error or warning and produced an EV of 25.037 expected hires/week for C0001 (a physically impossible number — more than one candidate can have per week). The bias audit's headline EO_gap reduction figure collapsed from 93.5% to 27.4%, entirely due to this one row. **Worse:** Hard Stop 2 (low-confidence flag) stopped firing for one additional candidate (212/213 instead of 213/213) — the corrupted, inflated point estimate made the tool APPEAR more confident, not less, because relative interval width shrinks as the point estimate grows for roughly fixed variance. | We expected the corruption to produce visibly wrong output (it did), but did NOT expect it to also suppress a safety flag rather than trigger one — this is the most valuable finding from this break attempt. |

### Did not test

- We did not test behavior under a genuinely empty or zero-row gated population (an edge case that would likely crash `bias_audit.py`'s group-mean division).
- We did not test concurrent/simultaneous runs writing to the same output files.
- We did not test any real integration with an external data source (e.g. an actual ATS or SEC filing feed) — this tool only ever operates on synthetic or manually-edited local CSVs.

### Broke during testing, fixed

- The bias audit report's naive-overshoot narrative was originally hardcoded
  to assert an overshoot happened; when the population was regenerated after
  adding a new field, the overshoot no longer occurred on that run, and the
  hardcoded text became false. Fixed by rewriting the report generator to
  describe whatever the current run actually produced, and by explicitly
  documenting the population-dependence itself as a finding (see
  `reports/adversarial_report.md`, Perturbation 1) rather than re-asserting
  the original result.

## Reflection

**What went well:** every component is grounded in a real, re-runnable
computation rather than an assertion — every number in every report can be
regenerated from the code, and we deliberately tested that by rerunning the
whole pipeline independently and confirming a match.

**What the tool got wrong / missed, and how we found out:** the calibration
constant used in the outcome policy (component 3) does not survive being
reused across an ordinary data refresh — we found this by accident (adding
one unrelated field shifted the safe calibration boundary by ~6x), not by
design, and it became one of the strongest findings in the whole project
once we investigated it properly instead of dismissing it as noise. The
break-attempt above surfaced a second, related weakness we had not
anticipated: the tool has zero defenses against corruption introduced AFTER
the GIGO gate has already run, and the resulting bad output can look MORE
trustworthy rather than less by the tool's own confidence metric.

**Next steps:** (1) make the GIGO gate re-runnable as a precondition check
immediately before allocation, not just once at generation time, so
post-gate corruption gets caught; (2) redesign Hard Stop 2's threshold to
compare candidates relative to their peers rather than to an absolute ratio,
since the current version both fires on 100% of the honest population and
can be fooled by a single corrupted row in the opposite direction;
(3) re-run `calibrate_shift.py` as a required precondition (already
enforced by Hard Stop 3) any time the population changes, rather than
treating a calibration constant as a one-time setting.
